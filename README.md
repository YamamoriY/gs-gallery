# gs-gallery

data_mori の 3D Gaussian Splatting アーカイブ。

`data_mori/成果物` の 3D Gaussian Splatting をブラウザで見られる形にまとめて公開するサイト。
公開先は https://yamamoriy.github.io/gs-gallery/ 。

## なぜ変換が要るか

学習の生の出力は 1 シーンあたり **1.2 GB 前後**（500万ガウシアン・SH次数3）ある。
そのままでは Web に置けないので、ノイズを落として間引いて SOG に詰め直す。

実測（`20260902_691`、元 407万点 / 1.00 GB）:

| | 点数 | サイズ |
|---|---|---|
| 元の PLY | 4,069,715 | 1.00 GB |
| ノイズ除去後 | 1,120,285 | — |
| 間引き後の PLY（100万点・SH無し） | 1,000,000 | 68 MB |
| **SOG（配信用）** | 1,000,000 | **約 12 MB** |

元の 1/80 前後。1 シーンあたり 2 分ほどで変換できる。

SOG は PlayCanvas の圧縮フォーマットで、中身は WebP テクスチャの ZIP。
「PLY 比 15〜20 倍」と言われるのは SH をフルに持った PLY との比較で、
SH を落としたあとの PLY からだと 5 倍前後になる。

## 技術スタック

- Next.js（静的書き出し）+ React + TypeScript + Tailwind CSS
- [SuperSplat Viewer](https://github.com/playcanvas/supersplat-viewer)（MIT）— 3DGS の描画
- [splat-transform](https://github.com/playcanvas/splat-transform) — 間引きと SOG 変換
- Python（numpy / scikit-learn / scipy）— ノイズ除去。uv で動かす
- GitHub Pages（GitHub Actions で自動デプロイ）

## 使い方

```
npm install
npm run viewer     # SuperSplat Viewer を public/viewer/ に書き出す
npm run convert    # 成果物の PLY を public/gs/*.sog に変換する（重い）
npm run scan       # data/scenes.json を作り直す
npm run dev
```

`npm run viewer` は一度でよい。新しいスキャンを足したら `convert` と `scan` を回す。
`convert` は [uv](https://docs.astral.sh/uv/) を使う。社内 CA などで証明書が
差し替えられている環境向けに `UV_SYSTEM_CERTS=1` を自動で立てている。

## ビューアの見え方

`scripts/build-viewer.mjs` が `public/viewer/settings.json` を作る。
ここを変えると全シーンの見え方が変わる。

- **背景は暗色** (`background.color = [0.1, 0.11, 0.1]`)。
  サイトが明るい配色なので白にしてみたが、このデータには合わなかった。
  森のスキャンは葉と葉の隙間から背景が透けるので、白だと隙間が白く抜けて
  穴だらけに見える。**暗さの問題ではないので明るさを持ち上げても直らない**
  (grading の brightness を 1.6 にしたら隙間がさらに目立って逆効果だった)。
  真っ黒は避けて僅かに green 寄りにし、明るいページの中で写真の枠のように
  見えるようにしている。`renderViewerHtml` にも同じ色を渡す。
  渡さないと最初のフレームが出るまで色が違ってちらつく。
- **カメラは `defaultSettings("object")`**。1 本の木を外から撮ったシーンなので、
  対象を画面に収める構えになる。`"environment"` (空間の中から見る) だと
  株全体が入らず、`20260831_596-599` はほぼ真っ白な画面になっていた。

## ノイズ除去

3DGS の出力には 2 種類のノイズが混ざっている。どちらも別の対処が要る。

**遠方に飛んだ巨大なゴミ** — `20260831_15tree` では、これのせいで
バウンディングボックスが 4.84km x 11.7km x 3.39km まで広がっていた。
中央値 ± 3σ の箱で落とす。ゴミは数が少ないので σ はさほど膨らまない
（`20260902_691` では座標の最大値が 600 を超える一方 σ は 29）。

**実体の中に混ざる靄** — 極端に平たい板や針状のガウシアン。
`20260902_691` では異方性（最長軸÷最短軸）が中央値 12 倍、上位 10% で 132 倍、
最大 230 万倍あった。被覆量（面積×不透明度）で見ると上位 1% の点が
全体の 19.5% を占めていた。

**ただし靄は形で切ってはいけない。** 3DGS は硬い面を「面に沿った平たい円盤」
で表すので、幹の樹皮は本質的に異方性が高い。異方性で切ると靄と一緒に
幹の表面が消えて中が透ける。詳しくは下の「形状フィルタを掛けない理由」。

`scripts/denoise/denoise.py` が両方をまとめて処理する。

```
1. 中央値 ± 3σ の箱で遠方のゴミを落とす
2. DBSCAN で一定サイズ以上のクラスタ = 「芯」を取る
3. 芯を平面グリッド（0.5m）に焼いて footprint を作る
4. footprint の中にある点を 1. の点群から全部拾い直す
5. 形と不透明度で絞る（既定では掛けない）
```

### 形状フィルタを掛けない理由

以前は 5 で `maxScale 0.15 / maxAniso 30 / minOpacity 0.15` を掛けていた。
黒い背景で見比べて決めた値で、靄は確かに消えていた。

だが背景を白にすると**幹の中が透けている**ことが分かった。3DGS は硬い面を
「面に沿った平たい円盤」で表すので、樹皮は本質的に異方性が高い。
`maxAniso 30` は幹の表面を作るガウシアンごと落としていた
（異方性の中央値は 12、上位 10% で 132）。
黒背景では幹が黒く沈むので、抜けていても分からなかった。

`20260902_693` で切り分けた結果:

| 形状フィルタ | 点数 | サイズ | 幹 |
|---|---|---|---|
| 現行 (0.15 / 30 / 0.15) | 100万 | 12.4 MB | 透ける |
| 緩和 (0.25 / 60 / 0.05) | 192万 | 23.6 MB | 透ける |
| 異方性のみ無効 | 100万 | 12.3 MB | 見えるが林床が抜ける |
| **なし** | **100万** | **12.3 MB** | **埋まる** |
| なし | 246万 | 30.0 MB | 完全に埋まる |

**点数ではなく種類の問題だった。** 点数を倍にしても透けたままで、
フィルタを外せば同じ点数・同じ容量で埋まる。中途半端に緩めるのも駄目で、
半透明のガウシアンも隙間を埋める役割を持っている。

掛けたいシーンだけ `scenes.overrides.json` の `denoise` に書く。

要点は **DBSCAN を除去そのものではなく「実体がどこにあるか」の判定にだけ使う**こと。
DBSCAN の結果をそのまま採ると疎な葉が全部ノイズ判定になる
（`20260902_691` では最大クラスタが原データの 16.7% しかなく、
未分類が 67% だった）。footprint を取って拾い直すと 46% まで戻る。

`eps` は固定値ではなく、min_samples 番目の近傍までの距離の中央値から決める。
`20260902_691` で 0.244、`20260831_15tree` で 0.271 と、密度に追従する。

> gs-classifier の `denoise_2d_dbscan` を出発点にしている。
> ただし既定の `radius=0.1`（eps=0.2, min_samples=50）と
> 「最大クラスタだけ残す」戦略はこのデータには合わなかった。
> 単木のような密で連結した対象向けの値で、歩きながら撮った林分には
> 効きすぎる。

### シーンごとに変える

`data/scenes.overrides.json` の `denoise` で切り替える。

```json
{
  "20260831_15tree": { "denoise": "box" },
  "20260902_693":    { "denoise": { "maxScale": 0.2 } }
}
```

| 値 | 意味 |
|---|---|
| 省略 | 上の 1〜5 を全部やる（既定） |
| `"box"` | 遠方ノイズを箱で落とすだけ。実体は一切削らない |
| `false` | 何もしない |
| オブジェクト | 既定値を部分的に上書き |

`"box"` は全体を見せたいシーン向け。`20260831_15tree` と `20260831_15tree_2`
がこれを使っている。

### 立木が測れていないとき

緯度経度は `null` にできる。番号と直径だけ分かっている木は一覧に「位置未登録」
と出て、地図には出ない。分からない位置を埋めるより、空にしておく方が安全。

シーン名から自動で決まる立木番号を変えたいときは `"trees": ["596", "599"]`
のように書く。`20260831_596-599` は 596〜599 の 4 本が写っているが、
597 と 598 は細く大径木として扱っていないので台帳には載せていない。

### 品質の調整

`scripts/config.mjs` の `PRESETS`（点数と SH）と `DENOISE`（ノイズ除去）で決める。

```
npm run convert -- --preset balanced      # 200万点・SH1
npm run convert -- 20260902_693 --force   # 1シーンだけ作り直す
npm run convert -- --keep-ply             # 中間の PLY を .cache に残す
```

| プリセット | 点数 | SH | 想定サイズ |
|---|---|---|---|
| `light`（既定） | 100万 | 0 | 12 MB 前後 |
| `balanced` | 200万 | 1 | 40 MB 前後 |
| `high` | 400万 | 2 | 100 MB 超 |

`DENOISE` の既定値は `20260902_691` で見比べて決めた。
これより強くすると葉が粒に分かれて疎になり、弱くすると緑の靄が残る。

| | 既定 | 強くする | 弱くする |
|---|---|---|---|
| `maxScale` | 0.15 m | 0.12 | 0.20 |
| `maxAniso` | 30 | 20 | 50 |
| `minOpacity` | 0.15 | 0.20 | 0.10 |

元データの場所は環境変数 `MORI_DATA_ROOT` / `MORI_SOURCE_DIR` /
`MORI_PROJECTS_DIR` で差し替えられる。

## 標準地

林分をまとめて撮ったスキャンは立木ではなく**標準地**として扱う。個体ではなく
区画を指すので、立木番号と胸高直径ではなく林班番号と面積で管理する。
`data/plots.json` に置き、`scenes.overrides.json` の `plot` で結び付ける。

```json
{ "20260831_15tree": { "plot": "15tree" } }
```

**面積は実測値だけを書く。** footprint から計算もできる (`20260831_15tree` なら
196,290 m2) が、スケールを信頼できる形で得られていないので出さない。

広域のスキャンは単木とは数字の桁が違う。`20260831_15tree` は footprint が
196,290 m2 で、単木シーン (523〜3,854 m2) の 50〜380 倍。DBSCAN の eps も
2.419 と単木 (0.20〜0.28) の 10 倍になる (密度から自動で決まるので問題ない)。

> **`"denoise": "box"` は広域スキャンに使えない。** 遠方ノイズが 1.5km 四方に
> 散っていると中央値 ± 3σ の箱が 1560 x 995 x 1711 になり、間引きの空間分割が
> 破綻して止まる。DBSCAN と footprint を使う既定の処理なら通る。

広域のスキャンから幹ごとに分割できるようになれば、標準地を親にしてその中の
単木を並べる形にできる。いまはその技術が無いので切り離してある。

## 林班界を地図に重ねる

北海道オープンデータポータルの「森林計画資料 (一般民有林) 渡島地域」の
shapefile から、対象地の周りだけを GeoJSON にして地図に重ねられる。

```
uv run --project scripts/pytools python scripts/pytools/compartments.py   <森林計画資料>.shp public/compartments.geojson   --centre 42.1064,140.6817 --radius 2500
```

`public/compartments.geojson` があれば地図に「林班界」ボタンが出る。
無ければボタンごと出ない (ファイルの有無を見て判断している)。

航空写真が見えなくなるので**塗らずに境界線と番号だけ**出す。

- 元データは EPSG:2459 (平面直角座標系 XI 系)。EPSG:4326 に変換する
- 地域全体だと数十 MB あって GitHub Pages に載らないので、
  `--radius` で対象地の周りだけ切り出す
- 森林簿の項目名は自治体ごとに揺れるので、
  `compartments.py` の `FIELD_ALIASES` で拾える名前を並べている

[YamamoriY/naragare-viewer](https://github.com/YamamoriY/naragare-viewer)
が同じデータを Leaflet で使っている。あちらは標準ライブラリだけで
shapefile を読んでいるが、こちらは変換を一度やって GeoJSON にするだけなので
pyshp と pyproj を使っている。

## 立木と位置

伐採に行くところまで使うので、3DGS を現地の立木と結び付けている。

実体は「地点」ではなく **立木 (幹) 1 本**。萌芽更新した株では 1 つの株から
出た複数の幹をまとめて 1 回で撮っていて、幹ごとに番号も直径も違うため。
`20260902_687-688` は 687 (34cm) と 688 (38cm) の 2 本、
`20260902_689-691` は 689・690・691 の 3 本が同じ株から出ている。

立木は `data/trees.json` に置く。シーンとの対応は成果物のファイル名から
自動で決まる。

```
20260902_684       -> 684
20260902_687-688   -> 687, 688
20260902_689-691   -> 689, 690, 691
```

番号でない名前のシーンに立木を結び付けたいときだけ、
`data/scenes.overrides.json` に `"trees": ["684"]` と書く。

### 座標の精度

元の測定値は度分秒で、秒が 0.1 秒刻み。地上でおよそ 3 m 相当なので、
`trees.json` に十進度が下 6 桁まで書いてあっても実際の精度はそこまで無い。
596・599 の株だけは iPhone の動画データから取った小数 4 桁で、
緯度およそ 11m・経度およそ 8m とさらに粗い (これ以上は取れない)。
**幹の同定は番号と直径で行い、座標は現地に着くまでの目安として使う。**

689・690・691 は位置を測っていないので、684 と 692 の中点に置いている。
`positionEstimated` に記録は残しているが、画面には出していない。

### 位置の出どころ

Google マップの共有リスト「ミズナラ_直径測定」(石川哲平) の 10 地点と、
別途もらった立木ごとの実測値 (番号・直径・度分秒) を突き合わせて作った。
10 本すべてが 1 対 1 で一致し、ずれは 0.0〜1.7 m だった (秒が 0.1 秒刻み
なので誤差の範囲)。地図リストの並び順は立木番号の逆順だったので、
並び順から対応を推測しなくて正解だった。

## スケール (いまは出していない)

再構成のスケールは撮影ごとに任意なので、シーンごとに違う。写り込んでいる
**橙色のヘリポート (一辺 50cm)** を物差しにして自動で測ろうとしたが、
**検出が信用できないと分かったのでサイトからは外した。**

```
npm run scale     # data/scale.json を作る (いまは参考値)
```

### なぜ信用できないか

やっていたのは「橙色っぽく、平らで、正方形に近い塊を探す」だけで、
それが目印である確認をしていない。森の落葉や土がこの条件を満たすと拾う。

実際 `20260902_687-688` の検出箇所 (2.65 × 2.98 ユニット、正方形度 0.888)
を切り出して描画したら、**葉しか写っていなかった**。
正方形度が高いのは「そういう形の塊を選んだ」からで、目印である保証にならない。
指標の作りが循環していた。

倍率は 0.18〜0.78m と 4.4 倍ばらついていたが、シーンの広がり (25〜47 ユニット)
と掛け合わせると実寸は 10〜17m に揃う。**もっともらしい数字に見えるが根拠が
無い**状態で、伐採判断に使われると危ない。

### 目印は橙色の「枠」

中央は白い円で、橙色は外周だけ。点がまばらだと枠が途切れて別々のかたまりに
割れ、細長い断片として拾われる (`20260902_693` で 0.71 × 1.78 になった)。
クラスタリングの距離を 0.12 から 0.20 に広げると繋がるが、
それでも目印かどうかの判定にはならない。

### これからどうするか

信頼できる値は `scenes.overrides.json` の `metresPerUnit` に手で書く。
RealityScan で目印の一辺が何ユニットかを測れば `0.5 ÷ 実測ユニット` で求まる。
値が入れば `src/lib/scenes.ts` の `sceneSizeMetres` を使って表示を戻せる。

目印の位置を人が一度指定して、その近傍だけを探す形にすれば誤検出はほぼ
無くなる。シーンごとに一度の手作業が要る。

## メタ情報の書き方

`scan` が自動で拾うのは点数・日付・元プロジェクト・写真枚数まで。
タイトルや説明は `data/scenes.overrides.json` に書く。`scan` を回し直しても消えない。

```json
{
  "20260902_693": {
    "title": "693 林班",
    "description": "下層植生の密なスギ林",
    "tags": ["スギ", "林班"],
    "location": { "latitude": 43.0, "longitude": 144.0 }
  }
}
```

成果物のファイル名と `projects/` のフォルダ名は完全には揃っていないので、
`scripts/project-match.mjs` が何段か緩めながら探す。当たらないものは
`sourceProject` を直接書く。`archive/2026-08-31_15tree_osmo_rigfocal` のように
区切りを含めて書くと `data_mori` のルートからの相対パスとして扱う。

> ### かつて名前が衝突していた (2026-09-07 に解消)
>
> 成果物だけ立木番号に振り直して `projects/` は撮影時の名前のままだった時期があり、
> 同じ番号が別の木を指していた（`projects/2026-09-02_693` は立木 696 の撮影だった）。
> これで 2 回取り違えが起きている。
>
> - 1 回目: `20260902_692` と `20260902_693` の PLY が完全に同一
> - 2 回目: 693 を学習し直したら 696 と同じ場所の再構成になった
>
> どちらも 2026-09-07 に学習し直して解消済み。座標系の中央値の差は
> 0.19 から 7.4 になった。
>
> `projects/` も立木番号に揃えたので、**いまは同じ番号のフォルダを使えば正しい**。
> 対応は動画サイズと画像枚数の比で検証した（`raw/2026-09-02/osmo/0902_<立木>.mp4`
> のサイズ ÷ `projects/2026-09-02_<立木>/images/` の枚数が全 10 組で
> 11.34〜11.48 MB/枚 に収まった。ばらつき 1.2%）。
>
> `npm run scan` が取り違えを検出する。元 PLY の指紋が一致するもの、
> 座標系の中央値が近く広がりも同程度のものを「取り違えの疑い」として出す。

### アーカイブから外す

`"hidden": true` を書くと一覧にも地図にも出ず、`npm run convert` も飛ばす。
PLY は成果物に残るので、`hidden` を消して変換し直せばいつでも戻せる。
`20260831_*` の 3 件がこれ。

## 一覧をカードではなく表にしている理由

同じ林分を同じ日に撮っているので、撮影写真をカードに並べても 10 枚が
ほぼ同じ緑になり、684 と 692 を見分ける役に立たない。木を選ぶときに効くのは
番号と直径なので、一覧は立木の表にしてある (直径で並べ替えられる)。
空間的な文脈は地図の航空写真が担っている。

行はシーンではなく立木 1 本ずつ。伐採する対象が幹だからで、萌芽更新した株は
1 シーンに複数の幹が入っているためシーンを並べると幹の数と合わない。
ただし直径も位置も分かっていない幹は互いに区別がつかないので 1 行にまとめる
(689・690・691 など)。同じ内容の行が並ぶだけで読みにくくなるため。

樹高 (`height`) と材積 (`volume`) は `data/trees.json` に枠だけ用意してある。
まだ正確に測れないので今は空。**1 本でも値が入るとその列が一覧に出る**ので、
測れたら JSON に書くだけでよい。

撮影写真からサムネイルを作る仕組み (`scripts/thumbs.mjs`) は入れていたが、
使わなくなったので消した。必要になったら git 履歴から戻せる。

## 構成

## 確かめたこと

- **20260902_693 は学習をやり直した** (2026-09-07) — 以前は 692 と PLY が
  完全に同一で、片方の木に固有の 3DGS が無い状態だった。
  再学習後は指紋もスケールも別物になり (1 ユニット 0.584m → 0.325m)、
  解消を確認した。**この種の取り違えはサイズも点数も同じなので気付きにくい。**
  成果物が増えたときは、サイズと数箇所のブロックで指紋を取って
  重複が無いか見ておくとよい。

- **上下の向きは正しい** — 撮影データのワールド上方向は 10 シーンとも `-y`
  (カメラ姿勢から算出。ばらつきは 0.02 以内なので重力に整列している)。
  3DGS の PLY は y 下向きが慣習で、SuperSplat Viewer はそれを解釈するため、
  そのままで正しく表示される。オフラインのラスタライザは生の座標で描くので、
  比較画像を作るときだけ `--camera-up 0,-1,0` を渡す必要がある。

## 分かっている問題

- **SOG の符号化はバイト単位では再現しない** — 同じ PLY を 2 回変換すると
  ファイルサイズと中身の統計は完全に一致するのにハッシュは変わる
  (WebP の符号化がスレッド数などに依存するため)。
  つまり用もなく `--force` を掛けると、中身は同じなのに git には新しい
  blob が積まれる。10 シーンで 120MB 増えるので、変換し直すのは
  パラメータを変えたときだけにする。

## 拡張の余地

- **樹高と材積** — `trees.json` に `height` を足せば一覧とシーンページに出る。
  3DGS から幹の直径を推定する経路は
  [gs-classifier](https://github.com/YamamoriY/gs-classifier) の幹抽出が使えるはず。
- **ビューアの差し替え** — `src/components/viewers/registry.ts` に登録する形にしてある。
  Babylon.js に替えるなら、Babylon は SOG を読めないので
  `scripts/convert.mjs` の出力を `.spz` に変える必要がある（splat-transform は対応済み）。
- **LOD** — splat-transform は LOD 出力に対応している。シーンが重くなったら検討する。

## 投稿フォーム (凍結中)

現地で見つけた木を動画・位置・直径つきで投稿してもらい、保守側が 3DGS に
して反映する、という構想を検討した。2026-09-07 時点で凍結。
再開するときのために、決まっていたことだけ残す。

- 想定利用者は森林組合の職員と町役場の林務家。技術者ではない
- **座標は手入力させない。** スマホの GPS から取る。
  度分秒の手入力は必ず打ち間違える (この README の「位置の出どころ」参照。
  実際に経度 `410.40564` という値をもらって、140 の打ち間違いと判断した)
- **林内は電波が届かない。** 送信時に通信を要求する作りだと現地で使えない。
  端末に溜めて圏内で送る形にする
- **立木番号は投稿者が持っていない。** 684〜696 は既存の現地タグの番号で、
  新しく見つけた木には無い。番号なしで投稿でき、保守側が採番する
- **動画のサイズが全体の構造を決める。** 位置や直径はテキストなので何とでも
  なるが、360 度動画は 1 本 1〜3GB ある。GitHub Pages はアップロードを
  受けられないので、置き場 (R2 や Drive) と認証を別に用意することになる。
  フォームは位置・直径・動画へのリンクだけ受け取る形なら実装量が小さい
